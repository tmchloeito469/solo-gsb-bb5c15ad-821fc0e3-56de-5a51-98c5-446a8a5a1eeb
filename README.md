# 展馆水路检修隔离方案搜索

一个纯前端网页工具（Node.js + Vite + TypeScript）：粘贴展馆供水管网拓扑 JSON，指定供水点、漏点和必须不断水的保供出口，可自动搜索最优关阀组合（检修隔离方案制定），可对各保供出口做「保供韧性巡检」（评估其在当前阀门开闭状态下的抗管段失效能力），可做「供水能力核验」（按各供水点供给上限与各出口需求量，求当前阀门状态下的总供给最大分配、各出口缺口，并给出一组限制总供给的最小割项目），可将部分保供出口标为「重点」做「重点出口优先配水」（先让重点出口总获配量最大，再在不减少该值的前提下让全部出口总获配量最大，第二阶段经残量网络改派已有流量），还能给出「管段增容建议」（沿用同一拓扑与供给上限 / 出口需求，枚举将参与输水管段容量由 1 提至 2 的改造方案，最多改造两条，推荐总获配量最高的方案），可做「双阀意外关闭风险扫描」（沿用拓扑、阀门登记状态与供水能力填写表，仅对当前开启的阀门模拟单阀或两阀意外关闭，最多处理 20 个开启阀门，以场景获配量比基线减少的数值作为新增缺口，按新增缺口降序、阀门编号列表字典序展示全部有损场景，并把两阀新增缺口严格大于两个单阀新增缺口之和的场景标为协同失供），可做「阀门状态异常定位」（以登记的阀门开闭状态为基线，枚举最多两处状态翻转，找出能同时解释现场有水 / 无水观测的阀门，并展示翻转后的开闭状态），还可做「单阀异常观测点规划」（沿用拓扑与供水点，把登记状态与每个阀门单独翻转分别作为假设，按最多 12 个候选观测节点的有水 / 无水签名归并不可区分组，并搜索能区分任意两组的最少观测点集合，同数按节点名称升序列表字典序推荐，展示各组在推荐点的预期状态），并能做「复水开阀顺序规划」（沿用拓扑、供给上限与出口需求，以当前登记为关闭的阀门为待开清单，最多 8 个，每步仅开启一个待开阀门、其余登记状态保持不变，按无向管段共享容量模型重算每步最大获配，选择使各步开阀后总获配量之和最大的完整开阀顺序，同分按阀门编号序列字典序取最小），还能做「关阀作业路线」（在关阀方案结果中选择一个方案，以该方案待关闭阀门为必访点，另填作业通道 JSON 与出发路点：先求路点间最短通行距离，再用子集动态规划求从出发点出发并返回、总步行时间最少的完整路线，同耗时按关阀操作的阀门编号序列字典序取舍，允许重复经过路点与通道；最多处理 8 个必访阀门），并能做「应急送水站布点」（沿用当前拓扑、供水能力填写表与作业通道 JSON，先以供水能力核验的各出口缺口作为待送水量；填写最多 8 个候选站路点、每站可送水量、最大步行分钟与出口到取水口路点的 JSON 映射，按通道最短步行距离建立站点到出口的可服务关系，枚举站点子集并用容量流分配整数送水量，选能补齐全部缺口且站数最少的方案，同数按站点名称升序列表字典序；展示站点、逐出口分配与总补齐量，无解时说明未补齐出口，缺口全为 0 时提示无需布点），还能做「检修阀门操作时段审计」（沿用当前拓扑、供水点、漏点与保供出口，输入起止整数分钟及最多 100 条实际操作记录（分钟、阀门编号、目标开闭），从登记状态起按分钟回放；同分钟对不同阀门的操作作为一次原子变更，同分钟重复操作同一阀门、未知阀门或越界时间报错；每次变更后按无阀管段与开启阀门重算供水点可达节点，以左闭右开区间记录漏点仍连通供水点的带压时段与各出口无法连通任一供水点的断水时段，合并相邻同类区间并展示逐出口累计断水分钟；空日志按登记状态覆盖整段，测算不改原始状态）。

## 功能

- 管网建模：节点、无阀管段、带唯一编号阀门的管段（含开/关状态），按无向图处理；
- **关阀方案搜索**：对**最多 12 个当前开启的阀门**枚举关阀组合，判定条件：
  1. 漏点与**所有**供水点断开；
  2. 每个保供出口仍能连通**至少一个**供水点；
- 优选规则：**关阀数最少**优先；同数时按「阀门编号升序列表」的**字典序**取舍，并列出全部最优方案；
- 展示每个方案的关阀清单、漏点隔离结果、各保供出口连通状态及可达供水点；
- 无解时给出明确提示与排查建议；
- **保供韧性巡检**：沿用页面上的「供水点」与「保供出口」，按当前阀门开闭状态，对每个出口计算**使其失去全部供水至少需失效的不同管段数**，并给出一组达到该数量的管段编号，供安排巡检；
  - 无阀管段与**开启**的带阀管段均按**单条失效**计；**已关闭的阀门不参与**；
  - 多个供水点作为**整体**（须与全部供水点同时断开才算失供）；
  - 环路、并行管段各自独立计数（最小边割 / 最大流模型）；
  - **已断水**出口显示 `0` 与空清单；出口与供水点同名时提示「无法按管段失效评估」；
  - 结果按所需失效数**升序**展示，数值越小越薄弱、越应优先巡检；
- **供水能力核验**：为每个供水点填写非负整数**供给上限**、为每个保供出口填写非负整数**需求量**，按当前阀门开闭状态求**总供给最大分配**（最大流）：
  - 展示总获配 / 总需求 / 总缺口、每个出口的**获配量与缺口**（足额 / 缺口标记），以及各供水点的上限、已供出与富余；
  - 展示**一组限制总供给的最小割项目**，每项标注类型——**供给上限**（供水点）、**管段**（无阀管段或开启阀门的编号，容量 1）或**出口需求**（出口名），项目容量合计恰等于总获配量（最大流 = 最小割）；
  - 每条连通管段容量均为 **1**，同一无向管段**双向合计只能占用一次**（共享容量，净流量绝对值 ≤ 1）；**已关阀不参与**；
  - 多供水点的不同上限与多出口的不同需求经最大流**同时约束**；
- **重点出口优先配水**：在同一填写表中为每个保供出口选择**重点 / 普通**（默认普通），沿用与核验完全相同的模型，做两级字典序最大化：
  - **第一级目标**：使重点出口**总获配量最大**；
  - **第二级目标**：在**不减少**重点总获配量的前提下，使**全部出口总获配量最大**；
  - 两阶段在**同一网络**上连续增广：第一阶段只挂重点出口的汇点弧求最大流；第二阶段在其**残量网络**上补挂普通出口汇点弧继续增广，增广路可穿过第一阶段流量的反向弧**改派已有流量**（如把某重点出口从一条管段换到另一条管段、腾出原管段供普通出口），避免逐出口占管造成的**虚假缺口**；
  - 页面展示**两级目标值**（重点总获配、全部总获配及各自缺口）与每个出口的**类别、需求量、获配量、缺口**，供与「供水能力核验」对照；**未选重点出口**时结果与普通核验的总获配量**完全一致**；
- **管段增容建议**：沿用页面上的拓扑、供给上限与出口需求，在当前阀门状态下枚举增容改造：
  - 仅将**参与输水的不同管段**（无阀管段 + 当前开启的带阀管段）容量各由 **1 提至 2**，**最多改造两条**；**已关阀及自环不可选**；
  - 分别计算**不改造（基线）、单条改造、两条组合改造**的总获配量——两条组合与单条一并比较，因此「**两条一起改造才产生收益**」（如两条串联瓶颈管段）的情形也能被识别；
  - 推荐取舍：**总获配量最高 → 改造条数最少 → 管段编号（升序）列表字典序最小**；
  - 页面展示基线与推荐总获配量、增量和改造管段编号；**零增量时提示无需增容**；
  - 仅为方案测算，**不改写拓扑，也不影响供水能力核验的结果**；
- **双阀意外关闭风险扫描**：沿用页面拓扑、阀门登记状态与供水能力填写表（供给上限 / 需求量），**不改登记状态**：
  - 仅对**当前开启**的阀门（**最多 20 个**）模拟**单阀意外关闭**与**两阀同时意外关闭**，共 n + C(n,2) 个场景；已关阀不参与；
  - 每个场景按与「供水能力核验」完全相同的模型（无向管段双向共享容量 1、已关阀不参与）重算**最大获配**，被模拟关闭的阀门对应管段临时移除；
  - 以「场景获配量比基线减少的数值」为**新增缺口**，仅列出新增缺口 > 0 的**有损场景**，按**新增缺口降序、阀门编号列表字典序**展示；
  - 两阀新增缺口**严格大于**两个对应单阀新增缺口之和时标为**协同失供**（两阀同时关闭的额外损失超出各自单独关闭之和，需优先排查）；
  - **无有损场景**时明确提示全部场景获配均不低于基线；
- **阀门状态异常定位**：沿用页面拓扑与供水点，分别填写现场观测到的**有水 / 无水节点**，以登记的各带阀管段开闭状态为基线，枚举**最多两处**状态翻转（开↔关，已关阀也可被翻为开）：
  - 每个候选按「无阀管段 + 实际开启的带阀管段」计算节点对任一供水点的可达性，**只用已观测节点**判定匹配（有水节点须可达、无水节点须不可达），未观测节点不参与；
  - 展示**翻转数最少**的全部匹配方案及翻转后的开闭状态；**零翻转**时提示登记状态与现场一致，**无匹配**时提示两处以内无法解释；
  - 校验供水点与观测节点存在、有水 / 无水两组观测不冲突；纯函数，不修改输入与原拓扑；
- **单阀异常观测点规划**：沿用页面拓扑与供水点，填写**最多 12 个候选观测节点**（不改拓扑）：
  - 把**登记状态**（零翻转）与**每个阀门单独翻转**（开↔关，已关阀也可被翻为开）分别作为一个假设，共阀门数 + 1 个；
  - 每个假设按「无阀管段 + 实际开启的带阀管段」计算各候选节点能否连通**任一供水点**，得到该节点的**有水 / 无水签名**；
  - 候选节点上**签名完全相同的假设归为不可区分组**并全部列出；对不同组搜索**能区分任意两组的最少观测点集合**（按点数 1, 2, … 枚举，同数时按**节点名称升序列表**的**字典序**推荐）；
  - 展示各组在推荐观测点上的**预期有水 / 无水状态**，并可展开查看全部候选点的完整签名（推荐点高亮）；
  - **全部假设同组**时明确提示：仅靠这些节点无法区分登记状态与单阀异常，需增设候选节点；
  - 校验供水点与候选节点存在、候选非空且不超过 12 个（自动去重）；纯函数，不修改输入与原拓扑；
- **复水开阀顺序规划**：沿用「供水能力核验」的拓扑、供给上限与出口需求，以及完全相同的最大流建模（无向管段双向共享容量 1、已关阀不参与）；**重点 / 普通类别不参与本规划**：
  - 以**当前登记为关闭**的阀门为**待开清单**（最多 8 个）：**超过 8 个**时提示无法规划，**空清单**时提示无需复水；
  - 规划一个完整开阀顺序：**每步仅开启一个待开阀门**，其余阀门保持登记状态不变，每步按现有共享容量模型**重算最大获配**；
  - 取舍规则：**各步开阀后总获配量之和最大**；同分按**阀门编号序列字典序**取最小；
  - 页面展示**基线总获配**、**每步开阀编号与该步总获配**、**累计获配**（各步总获配之和）与**最终开阀顺序**；
  - 纯函数测算：**不修改拓扑 JSON、登记的阀门状态与所填数值**；
- **关阀作业路线**：在关阀方案搜索结果中**选择一个方案**（默认选择推荐方案），另填**作业通道 JSON**（路点、无向通道及正整数步行分钟、各阀门对应路点）与**出发路点**：
  - 以所选方案**待关闭阀门为必访点**（最多 8 个），规划**从出发点出发、依次关闭全部必访阀门并返回出发点**的完整路线，**允许重复经过路点和通道**；
  - 先用 Floyd–Warshall 求**路点间最短通行距离**（并行通道取最小分钟，等耗时最短路按路点序列字典序取舍），再用**子集动态规划**求**总步行时间最少**的阀门访问顺序；**同耗时按关阀操作的阀门编号序列字典序**取最小；
  - 页面展示**阀门操作顺序**、**逐段实际通道路点**（出发段 / 阀门间转场段 / 返程段）、**分段耗时与总耗时**；
  - **无路可达**（出发路点或某些必访阀门路点互不可达，逐对列出）、**映射缺失**（必访阀门在 `valveWaypoints` 中缺少路点）或**必访阀门超过 8 个**时给出明确提示；
  - 作业通道是**独立于供水管网的步行网络**，路点无需出现在管网 `nodes` 中；路线测算**不修改拓扑 JSON、阀门登记状态与作业通道输入**；
- **应急送水站布点**：沿用当前拓扑、**供水能力填写表**（供给上限 / 需求量）与**作业通道 JSON**，先按当前阀门状态做一次供水能力核验，以各保供出口的**缺口作为待送水量**：
  - 用户填写**候选站路点**（最多 8 个，均须在作业通道 `waypoints` 中）、**每站可送水量**（非负整数）、**最大步行分钟**（非负整数）与**出口到取水口路点的 JSON 映射**（只需覆盖有缺口的出口）；
  - 在作业通道上用 Floyd–Warshall 求最短步行距离，站到某出口取水口的**最短步行 ≤ 最大步行分钟**时该站才可服务该出口（无路可达视为不可服务）；
  - **枚举站点子集**（按站数 0, 1, 2, … 升序），对每个子集构建**容量流**（超级源点 → 各站容量为可送水量、站 → 可服务出口容量为该出口待送水量、出口 → 超级汇点容量为待送水量）求**整数送水分配**；流值达到待送水量合计即该子集可补齐全部缺口；
  - 取舍规则：**能补齐全部缺口且站数最少**；同数时按**站点名称升序列表的字典序**取最小；
  - 页面展示选中**站点**（可送水量 / 已送出 / 富余 / 服务出口）、**逐出口整数送水分配**（各站送水量与步行分钟）与**总补齐量**；
  - **无解**时（全部候选站启用仍无法补齐）展示最多能送出的水量，并明确列出**仍未补齐的出口**；**缺口全为 0** 时提示**无需布点**；
  - 纯函数测算：**不改原始管网、阀门登记状态、供水能力数值与作业通道输入**；
- **检修阀门操作时段审计**：沿用当前拓扑、**供水点、漏点与保供出口**，输入**起止整数分钟**（区间**左闭右开** `[起, 止)`）与**最多 100 条实际操作记录**（每条含分钟、阀门编号、目标开闭，无需按分钟排序）：
  - 从阀门**登记开闭状态**起**按分钟回放**：同一分钟对**不同阀门**的操作作为**一次原子变更**——该分钟全部目标状态同时生效后才按「无阀管段 + 开启阀门」重算供水点可达节点；
  - **报错**情形：同分钟**重复操作同一阀门**、**未知阀门**编号、时间**越界**（分钟不在 `[起, 止)` 内）、记录结构 / 布尔值非法、记录超过 100 条、起止分钟非非负整数或起晚于止；
  - 以**左闭右开区间**记录**漏点仍连通至少一个供水点的带压时段**，以及**各保供出口无法连通任一供水点的断水时段**；**合并相邻同类区间**，展示**逐出口累计断水分钟**，并列出逐次原子变更明细与回放时间轴分段；
  - **空日志**（`[]` 或留空）时整段按**登记状态**覆盖；纯函数测算，**不改拓扑 JSON 与登记的阀门状态**；
- 求解均为纯函数，**不会修改输入 JSON 中的阀门状态**；
- 内置示例拓扑（展馆环状管网），一键载入体验。

## 快速开始（单条命令）

```bash
docker compose up --build
```

启动后用浏览器访问 **http://localhost:4173** （容器对外端口 **4173**），即可使用「搜索关阀方案」「保供韧性巡检」「供水能力核验」「重点出口优先配水」「管段增容建议」「双阀意外关闭风险扫描」「阀门状态异常定位」「单阀异常观测点规划」「复水开阀顺序规划」「关阀作业路线」「应急送水站布点」与「检修阀门操作时段审计」。无需任何外部账号或网络服务。

也可以不使用 Compose：

docker build -t water-isolation . && docker run --rm -p 4173:4173 water-isolation

## 拓扑 JSON 格式

```json
{
  "nodes": ["市政供水S1", "环管N1", "展厅A"],
  "pipes": [
    { "id": "P1", "from": "展厅A", "to": "环管N1" }
  ],
  "valvedPipes": [
    { "id": "V01", "from": "市政供水S1", "to": "环管N1", "open": true }
  ]
}
```

| 字段 | 说明 |
| --- | --- |
| `nodes` | 全部节点名称（非空字符串，不可重复） |
| `pipes` | 无阀管段，`id` / `from` / `to` 均为必填，`from`/`to` 必须是已声明节点 |
| `valvedPipes` | 带阀管段，额外要求布尔字段 `open`；阀门编号 `id` 在全网唯一 |

供水点、漏点、保供出口在页面表单中填写（多个用逗号/空格分隔），均为节点名称。

## 作业通道 JSON 格式（关阀作业路线）

作业通道是**独立于供水管网的步行网络**：路点无需与管网 `nodes` 同名或存在对应关系。

```json
{
  "waypoints": ["检修大门", "路口甲", "N1井位", "N2井位"],
  "passages": [
    { "id": "W01", "from": "检修大门", "to": "路口甲", "minutes": 3 },
    { "from": "路口甲", "to": "N1井位", "minutes": 4 }
  ],
  "valveWaypoints": {
    "V03": "N1井位",
    "V04": "N2井位"
  }
}
```

| 字段 | 说明 |
| --- | --- |
| `waypoints` | 全部路点名称（非空字符串，不可重复）；出发路点与全部阀门作业点都必须在此声明 |
| `passages` | 无向步行通道数组：`from` / `to` 为已声明路点，`minutes` 为步行通过分钟，必须是**正整数**；`id` 选填（仅供人工对照）；允许多条并行通道（自动取最短），自环忽略 |
| `valveWaypoints` | 阀门编号 → 该阀门作业所在路点；只需覆盖所选方案的必访阀门，缺少映射的必访阀门会被明确报出，多余映射忽略 |

出发路点在页面单独填写（必须包含在 `waypoints` 中），路线从该点出发并最终返回该点。

## 使用方法

1. `docker compose up --build` 后浏览器打开 **http://localhost:4173**；
2. 在「1. 管网拓扑 JSON」中粘贴拓扑，或点「载入示例拓扑」；
3. 在「2. 检修条件」填写**供水点**与**保供出口**（漏点仅供关阀方案搜索使用，巡检与核验不依赖它）；
4. 按需点击：
   - **搜索关阀方案**：列出最少关阀组合及各出口连通状态；
   - **保供韧性巡检**：下方表格按「至少需失效管段数」升序列出各出口，并给出一组该数量的管段编号作为巡检清单；
5. 「3. 供水能力核验、重点优先配水、管段增容、双阀风险扫描与复水开阀规划」：
   - 点击 **按上方供水点 / 保供出口生成填写表**（修改上方名单后可重新生成，已填同名数值与重点选择会保留）；
   - 在表格中为每个供水点填写非负整数**供给上限**、为每个保供出口填写非负整数**需求量**（留空按 `0` 处理），并用下拉框为每个保供出口选择**重点 / 普通**（默认**普通**）；
   - 点击 **核验供水能力**：右侧展示总获配 / 总缺口、每个出口的获配量与缺口、各供水点供出情况，以及一组限制总供给的最小割项目；
   - 点击 **重点出口优先配水**：右侧先展示第一级目标值（重点出口总获配）、再展示第二级目标值（不减少重点获配前提下的全部出口总获配），并列出每个出口的类别、获配量与缺口；未选任何重点出口时与「核验供水能力」总获配一致；
   - 点击 **管段增容建议**：右侧对比不改造、单条改造与两条组合改造的总获配量，给出推荐方案（基线与推荐总获配量、增量、改造管段编号）；零增量时提示无需增容；
   - 点击 **双阀意外关闭风险扫描**：右侧列出全部有新增缺口的单阀 / 两阀意外关闭场景（按新增缺口降序、阀门编号列表字典序），协同失供场景带标记；无有损场景时明确提示；扫描不修改登记的阀门状态；
   - 点击 **复水开阀顺序规划**：右侧以当前登记为关闭的阀门为待开清单（最多 8 个），给出使各步开阀后总获配量之和最大的完整开阀顺序，展示基线总获配、每步开阀编号与该步总获配、累计获配及最终顺序；待开清单为空时提示无需复水，超过 8 个时提示无法规划；规划不修改登记的阀门状态（示例拓扑中 V09 登记为关闭，可直接体验）；
   - 也可直接点「载入示例拓扑」，核验数值与重点选择（展厅B 为重点）会一并填好（示例：供给上限 市政供水S1=5、备用水箱S2=3；需求 展厅B=2、咖啡厅=1、卫生间=2）。
6. 「4. 阀门状态异常定位」：在**现场有水节点**与**现场无水节点**中分别填入观测结果（沿用上方拓扑与供水点，多个用逗号/空格分隔），点击 **定位异常阀门**：右侧列出翻转数最少的全部匹配方案（被翻转的阀门及翻转后的开闭状态）；零翻转表示登记状态与现场一致，无匹配表示两处以内无法解释。示例观测（有水：咖啡厅、卫生间；无水：展厅B → 定位为 V08 实际已关）会随「载入示例拓扑」一并填好。
7. 「5. 单阀异常观测点规划」：在**候选观测节点**中填入最多 12 个节点（沿用上方拓扑与供水点，多个用逗号/空格分隔），点击 **规划观测点**：右侧先把「登记状态 + 每个阀门单独翻转」等假设按有水 / 无水签名归为不可区分组，再给出能区分任意两组的**最少观测点集合**（同数按节点名称升序列表字典序推荐），并列出各组在推荐点的预期有水 / 无水状态；全部假设同组时会提示无法仅靠这些节点区分。示例候选（展厅A、展厅B、咖啡厅、卫生间、设备间 → 推荐观测点：卫生间、展厅B）会随「载入示例拓扑」一并填好。
8. 「6. 关阀作业路线」：先点击 **搜索关阀方案**，在右侧结果中**选择一个方案**（默认已选推荐方案，每个方案下有「选择该方案用于作业路线」按钮）；在 **作业通道 JSON** 中粘贴步行通道（示例可随「载入示例拓扑」一并填入），并填写**出发路点**，点击 **规划关阀作业路线**：右侧展示阀门操作顺序、逐段实际通道路点、分段与总耗时；无路可达、映射缺失或必访阀门超过 8 个时会明确提示。示例方案 [V03, V04] 从「检修大门」出发的两种操作顺序各 24 分钟，同分按阀门编号字典序取 V03 → V04。
9. 「7. 应急送水站布点」：沿用上方拓扑、第 3 步的供水能力填写表与第 6 步的作业通道 JSON。填写**候选站路点**（逗号分隔，最多 8 个）后点击 **按候选站路点生成可送水量填写表**，为每站填写非负整数**可送水量**，再填**最大步行分钟**与**出口到取水口路点的 JSON 映射**，点击 **规划应急送水站布点**：右侧以供水能力核验的各出口缺口为待送水量，给出能补齐全部缺口且站数最少的布点方案（站点、逐出口整数送水分配、各站用水情况与总补齐量）；全部候选站也无法补齐时列出未补齐出口，缺口全为 0 时提示无需布点。示例（展厅B / 咖啡厅 / 卫生间各缺 1，最大步行 6 分钟）推荐布设「环管N1井位 + 环管N3井位」共 2 个站、总补齐 3，会随「载入示例拓扑」一并填好。
10. 「8. 检修阀门操作时段审计」：沿用上方拓扑、**供水点**、**漏点**与**保供出口**，填写**起始 / 结束整数分钟**（区间左闭右开）与**实际操作记录 JSON**（数组，每项含 `minute` / `valve` / `open`，最多 100 条、无需按分钟排序；留空或 `[]` 即空日志），点击 **审计阀门操作时段**：右侧以左闭右开区间给出**漏点带压时段**与**逐出口断水时段**（相邻同类区间已合并）、**逐出口累计断水分钟**，并列出逐次原子变更（同分钟不同阀门同时生效）与回放时间轴；同分钟重复操作同一阀门、未知阀门或分钟越界会逐条报错。示例（区间 `[0, 60)`，第 5 分钟关 V03 / V04 / V05 隔离漏点并使咖啡厅、卫生间断水至第 30 分钟，第 50 分钟关 V08 使展厅B 断水 10 分钟）会随「载入示例拓扑」一并填好。

## 求解规则说明

### 关阀方案搜索

- 管网视为无向图；关闭阀门等价于移除该带阀管段；
- 仅对 `open: true` 的阀门进行组合搜索，数量超过 12 个时会提示先在输入中关闭部分阀门；
- 按关阀数 k = 0, 1, 2, … 依次枚举，找到可行解即停止，保证关阀数最少；
- 同一 k 下组合按编号升序列表的字典序生成，首个即推荐方案；最优方案超过 100 个时仅展示前 100 个；
- 漏点与供水点为同一节点、或开启阀门超限时，视为输入错误并明确提示。

### 保供韧性巡检

- 在当前阀门开闭状态下构建无向多重图：无阀管段全部计入，带阀管段仅 `open: true` 计入，已关阀（`open: false`）视为断开、不参与；
- 对每个出口，求解「供水点集合 → 该出口」的**最小边割**（各管段容量为 1，多供水点以无穷大容量的超级源点合并），其值即**至少需同时失效的不同管段数**，由最大流算法多项式时间求得，不受 12 个开启阀门上限影响；
- 给出的管段清单取**最贴近出口**的一个最小割，仅切断这些管段即可让该出口失去全部供水；
- 出口在当前状态下已无任何供水点可达时（如仅经已关阀门连接），所需失效数为 `0`、清单为空，并标记「已断水」；
- 出口节点名与某个供水点完全相同时，不存在「管段失效」能使其断水，标记「无法评估」并排在结果最后。

### 供水能力核验

- 在当前阀门开闭状态下构建无向多重图：无阀管段全部计入，带阀管段仅 `open: true` 计入，已关阀（`open: false`）视为断开、不参与；
- 构造单源单汇最大流网络：
  - 超级源点 → 每个供水点一条弧，容量为该点**供给上限**；
  - 每条参与输水的管段是一条**无向边**，两方向共享同一份容量 1：两个方向初始余量均为 1，推流后两弧余量之和恒为 1，因此同一管段双向合计至多占用一次（净流量绝对值 ≤ 1），不会出现一条管被两个方向同时各占 1；
  - 每个出口 → 超级汇点一条弧，容量为该出口**需求量**；
- 最大流值即**总供给最大分配**，同时满足全部供水点上限与全部出口需求约束（多上限、多需求一并生效）；
- 各出口汇点弧上的流量即**获配量**，`需求量 − 获配量` 即**缺口**；各源点弧流量即该供水点的实际供出量；
- 最大流后在残量网络上取源侧可达集合，饱和跨越割线的弧即**一组最小割项目**，可能是某供水点的供给上限、某条容量为 1 的管段（无阀管段编号或阀门编号）或某出口的需求量；其容量合计恒等于总获配量（最大流最小割定理）；容量为 0 的项目（零上限 / 零需求）不列入；
- 总获配为 0（供水点与出口完全不通，或上限 / 需求均为 0）时割清单为空并给出说明；
- 数值必须是**非负整数**（拒绝负数、小数、非数字与超出安全整数范围的值），留空按 `0`；校验为纯函数，不修改拓扑 JSON 与所填数值。

### 重点出口优先配水

- 沿用「供水能力核验」的**全部建模**：当前阀门开闭状态（已关阀不参与）、各供水点供给上限、各出口需求量，每条无阀 / 开启管段为双向共享容量 1 的无向边；
- 在填写表中把部分保供出口标为**重点**（其余为**普通**，默认全部普通），求两级字典序最优的分配：
  1. **第一级**：重点出口总获配量最大（等价于网络中只保留重点出口汇点弧时的最大流）；
  2. **第二级**：保持重点总获配不减少，全部出口总获配量最大；
- 实现方式为**同一网络上的两阶段连续增广**：第一阶段仅添加重点出口 → 超级汇点的需求弧并求最大流；第二阶段在第一阶段的**残量网络**上补加普通出口汇点弧，再求一次最大流；
- 第二阶段的增广路可以穿过第一阶段已分配流量的**反向残量弧**，即允许把重点出口已占用的管段**改派**到其他路径后腾出管段供普通出口使用，因此不会出现「逐出口贪心占管」导致的**虚假缺口**；第一阶段已达重点最大流，第二阶段任何增广路都不可能经重点出口汇点弧改变重点流量，故第一级目标值严格不减少；
- 各出口汇点弧上的流量即其**获配量**，据此给出类别（重点 / 普通）、需求量、获配量、缺口（需求量 − 获配量）与足额 / 缺口标记，并汇总**两级目标值**：重点总获配（含重点总需求、重点缺口）与全部总获配（含普通获配合计、总缺口）；
- 重点出口名单必须全部包含在保供出口名单中，否则报输入错误；名单重复时自动去重；
- **未选择任何重点出口**时第一级值为 0，第二级即普通核验的最大流，**总获配量与「供水能力核验」完全一致**，可直接对照；纯函数，不修改拓扑 JSON 与所填数值。

### 管段增容建议

- 沿用「供水能力核验」的拓扑、供给上限与出口需求，以及完全相同的最大流建模（无向管段双向共享容量、已关阀不参与）；
- 候选管段为**参与输水的不同管段**（无阀管段 + 当前开启的带阀管段），**已关阀及自环不可选**；
- 枚举**不改造、每条候选管段单独改造、每对候选管段组合改造**三种情形：被改造的管段容量由 **1 提至 2**，**最多改造两条**，分别用最大流计算总获配量（基线 + n + C(n,2) 次最大流，n 为候选管段数）；
- 两条组合与单条、基线**一并比较**，因此「单条改造无收益、两条一起改造才有收益」（如两条串联瓶颈管段）的情形会被正确识别并推荐；
- 推荐取舍：**总获配量最高 → 改造条数最少 → 管段编号（升序）列表字典序最小**；任何改造都无增益时推荐「不改造」，页面提示**无需增容**；
- 页面展示基线总获配量、推荐总获配量、增量与改造管段编号，并列出「不改造 / 单条最优 / 两条最优」三档对比；
- 纯函数测算：**不改写拓扑 JSON、供给上限与需求量，也不影响供水能力核验的展示结果**。

### 双阀意外关闭风险扫描

- 沿用「供水能力核验」的拓扑、阀门登记状态与填写表数值（供给上限 / 出口需求），以及完全相同的最大流建模（无向管段双向共享容量 1、已关阀不参与）；**重点 / 普通类别不参与本扫描**；
- 仅对**当前开启**的阀门模拟意外关闭：单阀场景 n 个 + 两阀场景 C(n,2) 个；开启阀门数**超过 20 个**时拒绝并提示先关闭部分阀门（防止组合爆炸）；已关阀与自环不参与；
- 每个场景把被模拟关闭的阀门对应管段**临时移除**后重算总获配（最大流），**不修改登记的阀门状态**；
- **新增缺口 = 基线总获配 − 场景总获配**；仅列出新增缺口 > 0 的有损场景，按**新增缺口降序**、同缺口按**阀门编号（升序）列表字典序**展示全部有损场景；
- **协同失供**：两阀场景的新增缺口**严格大于**两个对应单阀新增缺口之和（如两阀分别位于两条独立供水路径上，单关无损、同关断供）时标记，需优先排查；
- **无有损场景**时页面明确提示「全部场景获配均不低于基线」；
- 纯函数测算：不修改拓扑 JSON、登记的阀门状态与所填数值。

### 阀门状态异常定位

- 沿用页面拓扑 JSON 与「供水点」，另填写现场观测到的**有水节点**与**无水节点**；
- 以各带阀管段**登记的开闭状态**为基线，枚举**最多两处**阀门状态翻转（开→关或关→开，已关阀也可被翻为开），候选数为 1 + n + C(n,2)（n 为带阀管段总数），不受 12 个开启阀门上限影响；
- 每个候选按「无阀管段 + 实际开启的带阀管段」从全部供水点做连通性遍历：**有水观测节点须可达任一供水点、无水观测节点须不可达**；**只用已观测节点判定匹配**，未观测节点的通水状态不参与；
- 按翻转数 0、1、2 依次枚举，找到匹配即停止，保证**翻转数最少**；同一翻转数下组合按阀门编号升序列表字典序生成，全部匹配方案一并展示（超过 100 个仅展示前 100 个），每个方案给出翻转后全部阀门的开闭状态对照；
- **零翻转**匹配时提示登记状态与现场观测一致；**无匹配**时提示两处以内无法解释，需核对观测记录或考虑三处及以上异常、无阀管段破损等其他原因；
- 校验：供水点与观测节点必须已声明、至少填写一个观测节点、同一节点不能既在有水又在无水观测中（两组观测冲突）、供水点本身恒有水不能登记为无水；
- 纯函数，**不修改输入拓扑 JSON 与登记的阀门状态**。

### 单阀异常观测点规划

- 沿用页面拓扑 JSON 与「供水点」，另填写**最多 12 个候选观测节点**（自动按名称去重；为空或超限报输入错误），**求解不改拓扑**；
- 假设集合：**登记状态**（零翻转）与**每个阀门各自单独翻转**（开→关或关→开，已关阀也可被翻为开），共阀门数 + 1 个；
- 每个假设按「无阀管段 + 实际开启的带阀管段」从全部供水点做连通性遍历，候选节点**能连通任一供水点即有水、否则无水**，得到该假设在各候选节点（按名称升序排列）上的**有水 / 无水签名**；
- **不可区分组**：在全部候选节点上签名完全相同的假设归为一组（即只观测这些节点无法分辨组内究竟发生了哪个假设），组按其首个假设的顺序排列（含登记状态的组在最前）；
- **最少观测点搜索**：在候选节点中按点数 k = 1, 2, … 枚举子集，同一 k 下按「节点名称升序列表」的**字典序**生成，首个使任意两组在选中点上的状态组合两两不同的子集即推荐——因此保证**点数最少**，同数时取**字典序最小**；不同组在全部候选上签名必不相同，故只要组数 ≥ 2 就一定能找到推荐集合；
- 页面展示组数、推荐观测点与**各组在推荐点上的预期有水 / 无水状态**（现场观测后对照即可锁定到组），并可展开查看全部候选点的完整签名矩阵（推荐列高亮）；
- **全部假设同组**（如候选点只有恒有水的供水点、或无阀管段直连使任何单阀翻转都不改变通水状态）时标记为**不可区分**，不给推荐点，并提示需增设在不同假设下状态有差异的节点；
- 纯函数，**不修改输入拓扑 JSON 与登记的阀门状态**。

### 复水开阀顺序规划

- 沿用「供水能力核验」的拓扑、供给上限与出口需求，以及完全相同的最大流建模（无向管段双向共享容量 1、已关阀不参与）；**重点 / 普通类别不参与本规划**；
- **待开清单**为当前登记为关闭（`open: false`）的全部阀门，按编号升序列出：**超过 8 个**时拒绝并提示无法规划（防止组合爆炸），**空清单**时提示无需复水；
- 规划一个**完整开阀顺序**：从基线（不开启任何待开阀门）出发，**每步仅开启一个待开阀门**，其余阀门保持登记状态不变；每步的已开待开阀门集合确定后，按共享容量模型**重算总获配量**；
- 取舍规则：使**各步开阀后总获配量之和**（基线不计入，即第 1 步至第 n 步总获配之和）**最大**；同分按**阀门编号序列字典序**取最小（逐编号比较，与关阀方案搜索同一约定）；
- 实现方式：先预计算全部 2ⁿ 个「已开待开阀门子集」的总获配量（n 为待开阀门数，n ≤ 8），再用**子集动态规划**求最优顺序——f(S) = allocated(S) + max f(S\{v})，同分保留完整序列字典序最小者，保证精确最优而非贪心近似；
- 页面展示**基线总获配**、**每步开阀编号与该步总获配**、**累计获配**（截至该步各步总获配之和，最后一步即目标值）与**最终开阀顺序**；全部开完后总获配相对基线无净增时给出提示（瓶颈在供给上限、出口需求或其他管段）；
- 已关自环阀仍在待开清单中（需安排开启），但自环不参与输水，开启后不改变获配；
- 纯函数测算：**不修改拓扑 JSON、登记的阀门状态与所填数值**。

### 关阀作业路线

- 在关阀方案搜索结果中选择一个方案，以该方案**待关闭阀门**（去重后按编号升序）为**必访点**，另填与管网拓扑相互独立的**作业通道 JSON**（路点、无向通道及正整数步行分钟、各阀门对应路点）与**出发路点**；路线从出发路点出发、依次操作全部必访阀门并**返回出发路点**，**允许重复经过路点与通道**；
- **第一阶段——路点间最短通行距离**：在无向正权步行图上用 Floyd–Warshall 求全部路点对最短距离；同名端点间的并行通道取最小分钟；等耗时的最短路之间按**路点名称序列字典序**取最小（取名称最小的最短路上的首跳邻居，逐级递推得到完整序列）；
- **第二阶段——子集动态规划**：n 为必访阀门数（n ≤ 8），`dp[S][v]` 为从出发点出发、访问完集合 S 中阀门且最后操作 v 的最少步行分钟，转移 `dp[S][v] = min_{u∈S\{v}} dp[S\{v}][u] + dist(u, v)`，完整路线再加 `dist(v, 出发路点)` 闭合；同耗时按**关阀操作的阀门编号序列字典序**取最小；
- 重建路线时每个段（出发段 / 阀门间转场段 / 返程段）内部均取对应路点间的最短步行路径，因此段与段之间可能重复经过同一路点或通道；多个阀门映射到同一路点时其间转场耗时为 0；
- **明确报错**：必访阀门在 `valveWaypoints` 中缺少映射（`missing-map`，按编号列出）、必访阀门**超过 8 个**（`too-many`）、出发路点或任一必访阀门路点之间**无路可达**（`unreachable`，逐对列出关键位置）、作业通道 JSON 或出发路点校验失败（`invalid`）；所选方案无需关阀时总耗时为 0；
- 纯函数测算：**不修改拓扑 JSON、阀门登记状态与作业通道输入**。

### 应急送水站布点

- 沿用当前管网拓扑、**供水能力填写表**（各供水点供给上限、各出口需求量）与**作业通道 JSON**，先按当前阀门开闭状态执行一次与「供水能力核验」完全相同的最大流测算（无向管段双向共享容量 1、已关阀不参与），取每个保供出口的**缺口（需求量 − 获配量）作为待送水量**；**缺口合计为 0** 时直接提示**无需布点**，不再校验候选站；
- 用户输入：**候选站路点**（自动去重，最多 8 个，站名即其所在作业通道路点，重复或超限报错）、**每站可送水量**（非负整数，留空按 0）、**最大步行分钟**（非负整数，0 表示站与取水口须在同一路点）、**出口 → 取水口路点 JSON 映射**（有缺口的出口必须给出映射，路点须在 `waypoints` 中声明；已足额出口的多余映射忽略）；
- **可服务关系**：在无向正权作业通道上用 Floyd–Warshall 求路点间最短步行分钟（并行通道取最小，自环忽略），站 `s` 到出口 `o` 的取水口最短距离 `d(s,o)` 满足 `d(s,o) ≤ 最大步行分钟` 才可服务；无路可达或超限均视为不可服务；
- **容量流分配**：对给定站点子集构造整数最大流网络——超级源点 → 每站一条弧（容量为该站**可送水量**），站 → 其可服务出口各一条弧（容量为该出口**待送水量**），每出口 → 超级汇点一条弧（容量为**待送水量**）；最大流值即该子集最多能送出的水量，达到待送水量合计即**全部缺口可补齐**，各站→出口弧上的整数流量即逐站、逐出口的送水分配；
- **子集枚举**：按站数 k = 0, 1, 2, … 依次枚举（候选站先按名称升序排列，同 k 下按**站点名称升序列表字典序**生成），首个可补齐全部缺口的子集即推荐方案，故保证**站数最少**、同数时**字典序最小**；最多 8 个候选站，共至多 256 个子集；
- **无解**：全部候选站启用后容量流仍达不到待送水量合计时，展示「全部候选站最多送出量 / 总待送水量」、逐出口实送与未补齐量，并明确列出**仍未补齐的出口**（名称升序）及增设近站 / 提高可送水量 / 放宽步行分钟的建议；
- 纯函数测算：**不修改原始管网拓扑 JSON、阀门登记状态、供水能力填写数值与作业通道输入**。

### 检修阀门操作时段审计

- 沿用页面**当前拓扑、供水点、漏点与保供出口**（审计专用校验：供水点 / 漏点 / 保供出口均须是已声明节点，漏点不能同时是供水点；本审计**不受**关阀搜索「最多 12 个开启阀门」限制，也不依赖供给上限 / 需求量），**不改拓扑与登记的阀门开闭状态**；
- 审计区间为**整数分钟左闭右开** `[startMinute, endMinute)`：起止分钟必须是**非负整数**且 `start ≤ end`（允许 `start = end` 的零长度区间，结果为空）；
- 实际操作记录为 JSON **数组**（留空按空数组处理），最多 **100** 条，每条含：
  - `minute`：整数分钟，必须落在 `[startMinute, endMinute)` 内，否则报**越界时间**；
  - `valve`：阀门编号，必须是拓扑 `valvedPipes` 中已声明的编号，否则报**未知阀门**；
  - `open`：目标开闭的**布尔值**（`true` 开 / `false` 关）；
- **按分钟回放**：阀门运行态从**登记状态**（拓扑中各 `open` 字段）初始化；记录按分钟分组，变更分钟升序处理；
  - **同一分钟对不同阀门**的多条记录构成**一次原子变更**：该分钟全部目标状态先同时写入运行态，再**只重算一次**「无阀管段 + 实际开启的带阀管段」上从全部供水点出发的可达节点集合（无阀管段始终计入、自环忽略）；分钟内操作按阀门编号升序展示；
  - **同一分钟重复操作同一阀门**（不论目标是否相同）一律报错，不做回放；目标开闭与当前状态相同的无变化操作允许记录，仍计为一次变更；
- **时段记录（左闭右开）**：审计起点到首次变更前按登记状态计；每次变更自其分钟起生效，故区间在变更分钟处切分：
  - **漏点带压时段**：漏点仍可达**至少一个供水点**的区间（漏点与供水点连通即带压）；
  - **出口断水时段**：每个保供出口**无法连通任一供水点**的区间；
  - 相邻（前一区间 `to` === 后一区间 `from`）且同类的区间**自动合并**；逐出口给出**累计断水分钟**（各断水区间长度之和）；
- 页面同时展示**逐次原子变更明细**（分钟、各阀门前→后开闭、变更后漏点与各出口通断）与**回放时间轴分段**；
- **空日志**（`[]` 或留空）时不产生任何变更，整段 `[start, end)` 按**登记状态**覆盖；
- 纯函数测算：**不修改拓扑 JSON、登记的阀门状态与输入的操作记录数组**。

## 阀门操作记录 JSON 格式（检修阀门操作时段审计）

在页面中直接粘贴一个 JSON 数组（也可留空表示空日志），数组顺序任意，审计会按分钟重排；每条记录三个字段：

```json
[
  { "minute": 5, "valve": "V03", "open": false },
  { "minute": 5, "valve": "V04", "open": false },
  { "minute": 30, "valve": "V03", "open": true }
]
```

| 字段 | 说明 |
| --- | --- |
| `minute` | 操作发生的整数分钟，必须在页面填写的审计区间 `[起始, 结束)` 内（左闭右开，等于结束分钟即越界） |
| `valve` | 阀门编号，必须是拓扑 `valvedPipes` 中已声明的编号 |
| `open` | 目标开闭状态，布尔值：`true` 开启、`false` 关闭 |

- 同一分钟可出现多条**不同阀门**的记录，它们作为**一次原子变更**同时生效；同一分钟**同一阀门出现两次即报错**；
- 记录总数最多 **100** 条；空数组或留空表示整段无操作，按登记状态覆盖整段审计区间。

## 出口到取水口路点映射 JSON 格式（应急送水站布点）

应急送水站布点复用上方**作业通道 JSON** 的步行网络，另填一个简单映射：键为**有缺口的保供出口节点名**（管网节点），值为该出口取水口所在的**作业通道路点**。

```json
{
  "展厅B": "展厅B检修口",
  "咖啡厅": "咖啡厅取水口",
  "卫生间": "卫生间检修口"
}
```

- 只需覆盖**待送水量 > 0**（供水能力核验有缺口）的出口；已足额出口的多余映射自动忽略；
- 路点必须已在作业通道 JSON 的 `waypoints` 中声明；站到取水口的最短步行距离不超过页面所填**最大步行分钟**时，该站才可向该出口送水；
- 候选送水站路点与每站可送水量在页面表单中填写（最多 8 个站，可送水量为非负整数、留空按 0）。

## 容器构建说明

Dockerfile 为多阶段构建：第一阶段 `npm ci` 安装全部依赖并执行 `npm run build`（含 TypeScript 类型检查）；第二阶段仅拷贝 `dist/` 与零依赖的 `server.mjs`，镜像内不含开发依赖。除构建期安装 npm 依赖外，运行时不访问任何外部服务。
